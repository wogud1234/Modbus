# 시스템 콜(System Call)과 소켓(Socket)의 실체

> 약어는 처음 등장할 때 풀네임을 병기했고, 맨 아래 **부록**에 약어표를 정리했다.

---

## 0. 핵심 요약

| 질문 | 답 |
|---|---|
| 시스템 콜이란? | 사용자 모드 코드가 커널 모드 기능을 요청하는 **공식 진입 절차** |
| 시스템 콜 시 새 스레드가 생기나? | 아니오. **같은 스레드가 CPU 모드만 바꿔** 커널 코드를 실행하고 복귀 |
| 블로킹의 실체는? | 커널이 그 스레드를 스케줄러 대기 상태로 바꾸고 다른 스레드를 실행 |
| 소켓은 NIC를 추상화한 것인가? | **아니오.** 통신 끝점 하나의 프로토콜 상태와 버퍼를 담은 커널 객체 |
| NIC를 소프트웨어로 추상화한 것은? | NIC 드라이버 + NDIS 인터페이스 + 네트워크 어댑터 객체 |
| `stream.Read()`는 무엇을 하나? | 커널 소켓 구조체의 **수신 버퍼 → 앱 버퍼로 복사**(recv 시스템 콜). 복사된 만큼 커널 버퍼에서는 제거됨 |

## 1. 시스템 콜(System Call)

### 1.1 왜 필요한가

CPU(Central Processing Unit)는 실행 권한을 두 단계로 나눈다.

| 모드 | 이름(x86) | 할 수 있는 것 |
|---|---|---|
| 사용자 모드 | Ring 3 | 자기 프로세스의 메모리 접근, 일반 연산만 가능 |
| 커널 모드 | Ring 0 | 모든 메모리, 하드웨어(NIC 등), 특권 명령어 사용 가능 |

우리가 작성한 C# 코드는 사용자 모드에서 실행된다. 이 모드에서는 커널 메모리(소켓 테이블, TCB, 수신 버퍼)를 읽을 수 없고, NIC(Network Interface Card) 같은 하드웨어를 직접 제어할 수도 없다. 접근을 시도하면 CPU가 예외를 발생시킨다.

**시스템 콜은 사용자 모드 코드가 커널 모드 코드의 기능을 요청하는 공식 진입 절차이다.**

### 1.2 실제 동작 (x86-64 기준)

```
1. 사용자 코드가 인자(소켓 핸들, 버퍼 주소, 길이 등)를 레지스터/스택에 준비
2. syscall 명령어 실행 (CPU 특권 명령어)
3. CPU가 자동으로:
     - 실행 모드를 Ring 3 → Ring 0으로 전환
     - 미리 등록된 커널 진입 주소(MSR: Model Specific Register에 저장)로 점프
4. 커널이 시스템 콜 번호로 해당 처리 함수를 찾아 실행
     (예: recv → 소켓의 수신 버퍼에서 사용자 버퍼로 복사)
5. 결과를 레지스터에 담고 sysret 명령어 실행
6. CPU가 Ring 0 → Ring 3으로 복귀, 사용자 코드가 다음 줄부터 계속 실행
```

핵심: **같은 스레드가 모드만 바꿔서 커널 코드를 실행하고 돌아온다.** 새 스레드나 프로세스가 생기지 않는다.

### 1.3 Windows에서의 호출 경로

Windows에서는 앱이 `syscall` 명령어를 직접 쓰지 않고 DLL(Dynamic-Link Library)을 거친다.

```
C#  stream.Read()
 → .NET Socket.Receive()
 → P/Invoke(Platform Invocation, 관리 코드에서 네이티브 함수 호출)로
   ws2_32.dll의 recv / WSARecv 호출
 → ntdll.dll의 Nt... 스텁(stub, 얇은 진입 함수)
 → syscall 명령어   ← 여기서 Ring 3 → Ring 0
 → 커널: I/O(Input/Output) 관리자 → AFD.sys → tcpip.sys
 → 완료 후 sysret으로 복귀
```

- 소켓 I/O는 Windows에서 내부적으로 `NtDeviceIoControlFile` 계열 시스템 콜로 AFD(Ancillary Function Driver) 드라이버에 요청을 보내는 형태이다.
- `recv`, `send`, `accept` 같은 이름은 그 위의 API(Application Programming Interface) 이름이다.

### 1.4 비용과 블로킹

- 모드 전환과 인자 검증에 비용이 든다(대략 수백 ns 수준). 데이터 복사는 별도 비용이다.
- 시스템 콜 안에서 조건이 안 맞으면(수신 버퍼가 비어 있음 등) 커널이 **그 스레드를 스케줄러의 대기 상태로 바꾸고 다른 스레드를 실행**한다. 이것이 "블로킹"의 실체이다.
- 조건이 충족되면(패킷 도착) 커널이 그 스레드를 다시 실행 가능 상태로 만들고, 시스템 콜이 이어서 완료된다.

### 1.5 소켓 관련 호출 구분

| 호출 | 시스템 콜 경로를 타는가 |
|---|---|
| `socket()`, `bind()`, `listen()`, `accept()` | O |
| `recv()`, `send()` (`stream.Read()`, `stream.Write()`의 하위) | O |
| `client.GetStream()` | **X** (순수 .NET 객체 생성) |
| `new TcpListener(ip, port)` | X (필드 저장만) |

## 2. 소켓은 NIC를 소프트웨어로 추상화한 것인가

**아니오.** 소켓은 NIC의 추상화가 아니라 **통신 끝점(endpoint) 하나의 상태를 담은 커널 객체**이다.

### 2.1 소켓의 실체

커널 메모리에 있는 구조체이며, 대략 다음을 담는다.

```
- 프로토콜 종류 (TCP / UDP)
- 4-튜플: 로컬 IP, 로컬 포트, 원격 IP, 원격 포트
- TCP 상태 (LISTEN, ESTABLISHED, CLOSE_WAIT ...)
- TCB 정보: 송신/수신 시퀀스 번호, 윈도우 크기, 재전송 타이머
- 수신 버퍼, 송신 버퍼
- (LISTEN 소켓이면) accept 큐, SYN 큐
```

프로세스가 갖는 "소켓 핸들"은 이 커널 객체를 가리키는 **프로세스별 핸들 테이블의 인덱스**이다.

### 2.2 계층 구조에서의 위치

```
앱 (C# 코드)
  ↓ 시스템 콜
소켓                     ← 연결 하나의 상태 + 버퍼 (여기까지가 소켓 계층)
  ↓
TCP/IP 스택 (tcpip.sys)  ← 세그먼트 생성, 라우팅, 재전송
  ↓
NDIS                     ← NIC 드라이버 표준 인터페이스
  ↓
NIC 드라이버 → NIC 하드웨어
```

NIC를 소프트웨어로 추상화한 것은 소켓이 아니라 **NDIS 인터페이스와 그 위의 네트워크 어댑터(네트워크 인터페이스) 객체**이다.

### 2.3 소켓이 NIC의 추상화가 아닌 근거

1. **소켓과 NIC는 1:1이 아니다.**
   NIC 하나 위에 소켓이 수천 개 존재한다. 각 소켓은 4-튜플로 구분되고, 수신 프레임을 어느 소켓으로 보낼지는 TCP 스택이 4-튜플로 조회해 결정한다.

2. **소켓은 특정 NIC에 고정되지 않는다.**
   송신 시 어느 NIC로 내보낼지는 커널의 라우팅 테이블이 패킷마다 결정한다. `IPAddress.Any`로 bind한 소켓은 모든 NIC의 주소로 들어오는 패킷을 받는다. 소켓이 bind하는 대상은 NIC 하드웨어가 아니라 **IP 주소와 포트**이다.

3. **NIC 없이도 소켓은 동작한다.**
   `127.0.0.1`(루프백)로 통신하면 TCP 스택이 패킷을 NIC로 내보내지 않고 스택 내부에서 되돌려 수신 경로에 넣는다. 같은 PC의 두 프로세스가 소켓으로 통신하는데 NIC는 관여하지 않는다.

## 3. 소켓 버퍼와 Read / Write: 데이터는 어디서 어디로 가는가

**소켓 구조체(커널)가 수신/송신 버퍼를 소유하고, `Read` / `Write`는 그 커널 버퍼와 앱 버퍼 사이에서 데이터를 복사하는 시스템 콜을 호출하는 통로이다.**

### 3.1 수신: stream.Read()

```
[커널 메모리]                                   [앱 메모리(사용자 영역)]
소켓 구조체
 └─ 수신 버퍼: [Modbus 요청 바이트...]  ──recv 시스템 콜로 복사──→  byte[] buffer
```

1. 상대가 보낸 데이터는 커널이 받아서 그 연결 소켓의 **수신 버퍼**에 미리 쌓아 둔다. 이 과정은 앱이 Read를 호출하는 것과 무관하게 일어난다.
2. `stream.Read(buffer, 0, len)`을 호출하면 내부에서 `recv` 시스템 콜이 실행되어, 커널이 수신 버퍼의 데이터를 **앱이 넘긴 `buffer`(사용자 메모리)로 복사**한다.
3. 복사된 바이트 수가 `Read`의 반환값 `n`이다.

### 3.2 송신: stream.Write()

```
byte[] response  ──send 시스템 콜로 복사──→  소켓 구조체의 송신 버퍼  → (커널이 패킷화 / 전송 / 재전송)
```

`Write`는 앱 버퍼를 커널 **송신 버퍼로 복사**하고 리턴한다. 실제 전송은 커널이 이어서 처리한다.

### 3.3 알아둘 점

| 항목 | 내용 |
|---|---|
| 복사이면서 소비 | 커널 수신 버퍼에서 복사된 만큼은 버퍼에서 제거된다. 같은 데이터를 다시 읽을 수 없다. (`MSG_PEEK` 옵션은 제거 없이 볼 수 있으나 `NetworkStream.Read`에는 해당 없음) |
| `NetworkStream`의 역할 | 데이터를 들고 있지 않다. 소켓을 참조하는 래퍼일 뿐이며, 데이터는 커널 소켓 구조체의 버퍼에만 있다. 앱 쪽에서 데이터를 갖는 것은 우리가 넘긴 `buffer`이다. |
| 가져오는 양 | `buffer` 크기와 수신 버퍼에 쌓인 양 중 **작은 쪽**. 수신 버퍼에 200바이트가 있어도 `buffer`가 100바이트면 100바이트만 복사되고 나머지는 커널에 남는다. |
| 부분 수신 | 상대가 100바이트를 보냈어도 아직 60바이트만 도착했다면 60바이트만 반환될 수 있다. (TCP는 바이트 스트림이므로 메시지 경계가 없다) |
| 버퍼가 비어 있을 때 | 데이터가 도착할 때까지 호출 스레드가 블로킹된다. |
| `Write` 리턴 시점 | 상대가 받은 시점이 아니라 **커널 송신 버퍼에 복사된 시점**이다. 송신 버퍼가 가득 찬 경우에만 블로킹된다. |

## 4. 전체 정리

| 대상 | 정체 |
|---|---|
| NIC | 프레임을 전기/광 신호로 송수신하는 하드웨어 (DMA, 인터럽트 사용) |
| NIC 드라이버 + NDIS | 하드웨어를 커널에서 다루기 위한 소프트웨어 계층 |
| TCP/IP 스택 (tcpip.sys) | 프로토콜 처리(핸드셰이크, 세그먼트화, 재전송, 라우팅) |
| 소켓 | 통신 끝점 하나의 프로토콜 상태와 송수신 버퍼를 가진 커널 객체 |
| 소켓 핸들 | 프로세스가 그 커널 객체를 가리키는 번호 |
| 시스템 콜 | 앱이 소켓 객체에 대한 작업(accept / recv / send)을 커널에 요청하는 진입 절차 |
| 소켓 수신/송신 버퍼 | 커널이 소유한 메모리. `Read` / `Write`는 이 버퍼와 앱 버퍼 사이의 복사 |

즉 소켓은 "NIC를 감싼 것"이 아니라, **TCP/IP 스택이 관리하는 연결 상태를 앱이 시스템 콜로 조작할 수 있도록 노출한 객체**이다.

## 부록. 약어 / 용어 풀네임

| 약어 | 풀네임 | 설명 |
|---|---|---|
| CPU | Central Processing Unit | 중앙 처리 장치 |
| NIC | Network Interface Card | 랜카드. 프레임을 송수신하는 하드웨어 |
| DMA | Direct Memory Access | CPU 개입 없이 장치가 메모리에 직접 읽고 쓰는 방식 |
| NDIS | Network Driver Interface Specification | Windows의 네트워크 드라이버 표준 인터페이스 |
| AFD | Ancillary Function Driver | Windows 소켓 요청을 tcpip.sys로 연결하는 커널 드라이버 (AFD.sys) |
| tcpip.sys | TCP/IP 스택 드라이버 | Windows 커널의 TCP/IP 프로토콜 구현체 |
| DLL | Dynamic-Link Library | 동적 링크 라이브러리 (ws2_32.dll, ntdll.dll 등) |
| P/Invoke | Platform Invocation | .NET 관리 코드에서 네이티브 함수를 호출하는 기능 |
| MSR | Model Specific Register | CPU 모델별 특수 레지스터 (syscall 진입 주소 등을 저장) |
| I/O | Input / Output | 입출력 |
| API | Application Programming Interface | 응용 프로그램 인터페이스 |
| TCP | Transmission Control Protocol | 연결 지향, 신뢰성 있는 바이트 스트림 프로토콜 |
| UDP | User Datagram Protocol | 비연결형 데이터그램 프로토콜 |
| IP | Internet Protocol | 패킷 주소 지정 및 전달 프로토콜 |
| TCB | Transmission Control Block | 커널이 TCP 연결마다 유지하는 상태 구조체 |
| SYN | Synchronize | 연결 요청 플래그 (3-way 핸드셰이크 1단계) |
| Ring 0 / Ring 3 | CPU 보호 링 | Ring 0 = 커널 모드, Ring 3 = 사용자 모드 |
| 4-튜플 | (로컬 IP, 로컬 포트, 원격 IP, 원격 포트) | TCP 연결 하나를 유일하게 식별하는 값의 조합 |
| 루프백 | Loopback (127.0.0.1) | 패킷이 NIC로 나가지 않고 스택 내부에서 되돌아오는 주소 |
