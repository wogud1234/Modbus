# 1강 — KEPServerEX, OPC DA/UA, Modbus 슬레이브 구조

## OPC DA / UA

| 약어 | 풀네임 | 핵심 |
|---|---|---|
| OPC | OLE for Process Control → Open Platform Communications | 산업용 장비 데이터 교환 표준 |
| DA | Data Access | 1990년대 클래식 OPC. 현재값 읽기/쓰기/구독 위주 |
| UA | Unified Architecture | DA의 후속 표준 |

### DA vs UA 차이점

- **DA**: Windows COM/DCOM 기반 → Windows 전용, 네트워크 방화벽 설정 까다로움
- **UA**: 플랫폼 독립(Linux, 임베디드 가능), TCP 단일 포트, 인증서 기반 보안, 구조적 데이터(객체/메서드/이력) 표현 가능
- 새 시스템에는 **UA가 사실상 표준**. .NET에서는 OPC Foundation .NET SDK 또는 Opc.UaFx 사용

---

## KEPServerEX 역할

PLC, 모션 컨트롤러, 센서 등 다양한 장비와 통신 드라이버로 연결 → 데이터를 OPC DA/UA 등 표준 인터페이스로 제공하는 **통신 게이트웨이**.

---

## 이 프로젝트의 통신 구조

```
MES(마스터)  →  "주소 100번부터 10개 읽어줘" (FC03)  →  내 앱(슬레이브, 포트 502)
                                                          ↓
                                                  앱이 100~109번 데이터 조회
                                                          ↓
MES  ←  응답 프레임(16비트 값들)  ←  응답 전송
```

- **내 앱 = Modbus TCP 슬레이브** (포트 502에서 연결 대기)
- **MES = 마스터** (읽기/쓰기 요청을 보냄)
- .NET 구현: NModbus, EasyModbus 등 라이브러리 사용

---

## Modbus "레지스터를 읽는다"의 실제 의미

MES가 PC의 RAM을 직접 읽는 게 **아님**.

> Modbus의 "레지스터"는 하드웨어 메모리 주소가 아니라 **프로토콜상의 논리적 주소 공간**.  
> 슬레이브(내 앱)가 이 주소 공간을 직접 구현해서 응답할 뿐.

실제 동작 순서:

1. MES가 "주소 100번부터 10개 읽어줘" 요청 프레임 전송
2. 내 앱의 Modbus 서버 코드가 요청 파싱
3. 앱이 100~109번에 해당하는 값을 자기 데이터에서 조회
4. 값을 응답 프레임에 담아 전송
5. MES는 응답 프레임의 바이트를 받아 해석

### 슬레이브 응답 방식 두 가지

| 방식 | 구현 |
|---|---|
| 테이블 방식 | `ushort[]` 같은 배열(레지스터 맵)을 유지, 라이브러리가 주소에 맞춰 읽어 응답 |
| 요청 시 생성 방식 | 요청이 올 때 핸들러에서 주소를 보고 값을 계산해 응답 |

→ 둘 다 "앱 프로세스 안의 데이터"를 쓴다는 점은 동일. **앱이 노출하기로 한 값만** 읽힘.

---

## 구현 시 주의사항

| 항목 | 내용 |
|---|---|
| 데이터 크기 | 레지스터는 16비트 단위. float/int32 → 2개, double → 4개 레지스터 |
| 엔디안 | 워드/바이트 순서(Big/Little endian, word swap)를 MES와 맞춰야 함 → 값 이상의 1순위 원인 |
| 주소 체계 | 0-based, 1-based, 40001 방식이 갈릴 수 있음 → MES 측 확인 필요 |
| 스레드 동기화 | 요청 처리는 수신 스레드, 데이터 갱신은 다른 스레드 → `lock` 등 동기화 필수 |
| 스냅샷 일관성 | 여러 레지스터 값(예: X, Y 좌표)은 갱신 도중 읽히면 어긋남 → 한 번에 갱신하거나 버퍼 교체 |
| Function Code | FC03(읽기), FC04, FC06(단일 쓰기), FC16(다중 쓰기) 등 지원 범위 정의 |
| 예외 응답 | 범위 외 주소 요청 시 `Illegal Data Address` 등 예외 응답 처리 필요 |

## 추가 내용 (2026-10-03)

### OPC의 역할과 KepServerEX의 위치

OPC는 변환 프로토콜이 아니라 **표준화된 인터페이스(규격)**.  
현장에 난립하는 Modbus, PROFIBUS, EtherNet/IP 등 수십 가지 프로토콜을 각각 개별 드라이버로 만들지 않아도 되도록, OPC 서버가 드라이버를 내장하고 위쪽으로는 **통일된 OPC 인터페이스**를 제공한다.

```
[현장 장비들]           [OPC 서버]          [상위 소프트웨어]
  Modbus 장비   →  |               |  →   MES
  PROFIBUS 장비 →  |  KepServerEX  |  →   SCADA
  EtherNet/IP  →  |  (드라이버 내장)|  →   HMI
```

**KepServerEX**는 이 OPC 서버를 상용 제품으로 구현한 것 (제조사: Kepware, 현재 PTC 소유).  
수백 가지 드라이버 내장, OPC DA / UA 규격을 상위에 제공.

최종 구조:
```
[현장 장비(슬레이브)]  ←→  [KepServerEX(마스터)]  ←→  [MES/SCADA/HMI]
   내 ModSlave 앱            Modbus TCP 마스터           상위 시스템
```

### KepServerEX Modbus 디바이스 설정

#### Zero-Based Addressing

Kep이 태그 주소를 프레임에 담을 때 1을 뺄지 결정.

| 설정 | 동작 | 태그 400001 → 프레임 주소 |
|------|------|--------------------------|
| Enable (기본값) | 1을 빼서 전송 | 0 |
| Disable | 그대로 전송 | 1 |

- 앱 배열이 0-based면 **Enable이 맞음**
- 공식: `태그 번호 − 400001 = 배열 인덱스`
- 값이 한 칸 밀리면 이 설정을 먼저 의심

#### Zero-Based Bit Addressing

레지스터 안의 비트를 읽을 때 (예: `400001.0`) 첫 비트를 0번으로 볼지 1번으로 볼지.  
레지스터 단위로만 읽으면 영향 없음.

#### Holding Register Bit Writes

| 설정 | 동작 |
|------|------|
| Enable | 비트 전용 명령 한 번으로 처리 (별도 FC 지원 필요) |
| Disable | Read → Modify → Write 3단계 처리 |

앱이 비트 단위 쓰기를 구현하지 않았으면 **Disable이 안전**.

#### FC06 / FC16 쓰기 방식

| 설정 | 의미 |
|------|------|
| Enable | FC06 (Write Single Register) 사용 가능 |
| Disable | FC16 (Write Multiple Registers)만 사용 |

쓰기 시 **Illegal Function** 오류가 나면 앱 구현과 이 설정의 불일치가 원인일 수 있음.

#### NModbus 주의사항

NModbus DataStore는 내부가 **1-based**.  
프레임 주소 0 → `HoldingRegisters[1]`.  
직접 만든 배열이 아니라 라이브러리 저장소를 쓴다면 이 오프셋 확인 필수.

#### 검증 방법

1. 앱에서 첫 번째 레지스터에 `1111`, 두 번째에 `2222` 넣기
2. Modscan으로 주소 1번 읽어서 `1111` 확인
3. `1111`이면 정상, `2222`이면 한 칸 밀린 것 → Zero-Based 설정 조정

### KepServerEX6 채널 구조

채널(Channel)을 만들 때 드라이버를 선택하고, 그 안에 디바이스를 추가하는 구조:

```
KepServerEX6
└── Channel (채널)        ← 드라이버 + 통신 설정 묶음
    └── Device (디바이스) ← 실제 연결 대상 (슬레이브 앱)
        └── Tag (태그)    ← 읽고 쓸 데이터 포인트
```

- **Channel**: 어떤 프로토콜(Modbus TCP, RTU 등)로 통신할지 선택하는 그룹
- **Device**: 슬레이브 앱의 IP, 포트, 슬레이브 ID 등을 지정
- **Tag**: 실제로 읽거나 쓸 레지스터 주소와 데이터 타입 정의

---

### KepServerEX6 드라이버 개념

드라이버 = **특정 프로토콜/장비와 통신하는 방법을 캡슐화한 모듈**.

| 종류 | 예시 | 역할 |
|---|---|---|
| 하드웨어 드라이버 | 아진 보드 드라이버 | PC 슬롯에 꽂힌 물리 카드 ↔ 내 코드 사이의 API |
| KepServer 드라이버 | Modbus TCP 드라이버 | 네트워크/시리얼 프로토콜 ↔ KepServer 내부 데이터 사이의 변환 |

KepServerEX6 안에 수백 가지 드라이버가 내장되어 있고, 채널 생성 시 그 중 하나를 선택한다.

### Modbus TCP 통신 전체 흐름 (1초 주기 예시)

```
[1초마다 반복]

MES (OPC 클라이언트)
    ↕ OPC 프로토콜

KepServerEX6
  └─ Modbus TCP 드라이버
       ① Modbus 요청 패킷 생성 (Holding Register 읽기 요청)
       ② 내 앱으로 전송

내 앱 (ModSlave — 슬레이브)
       ③ Modbus 패킷 수신 및 파싱
       ④ Holding Register 값 꺼내서 Modbus 응답 패킷 생성
       ⑤ KepServer로 전송

KepServerEX6
  └─ Modbus TCP 드라이버
       ⑥ 응답 패킷 파싱 → 내부 데이터로 변환

MES (OPC 클라이언트)
       ⑦ OPC로 값 수신
```

- KepServer 드라이버는 **KepServer 내부 ↔ Modbus 프로토콜** 간 변환 담당
- 내 앱은 Modbus 프로토콜을 **직접 구현**해야 함 (NModbus 등 라이브러리 활용)

### Modbus 데이터 영역 4가지

| 영역 | 주소 | 타입 | 마스터 권한 |
|---|---|---|---|
| Coil (코일) | 0xxxx | 비트 (1bit) | 읽기/쓰기 |
| Discrete Input (디스크리트 입력) | 1xxxx | 비트 (1bit) | 읽기만 |
| Input Register (입력 레지스터) | 3xxxx | 워드 (16bit) | 읽기만 |
| **Holding Register (홀딩 레지스터)** | **4xxxx** | **워드 (16bit)** | **읽기/쓰기** |

KepServer가 Holding Register를 요청한다는 것은 **16bit 정수 데이터를 읽겠다**는 의미.
